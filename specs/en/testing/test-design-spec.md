# Nacos Node.js SDK Test Design Spec

This document defines how the Node.js SDK 3.x is tested and when a release may ship.
It follows the
[Java SDK Integration Test Spec](https://github.com/alibaba/nacos/blob/3.3.0/specs/en/testing/java-sdk-integration-test-spec.md).

The goal is **SDK scenario coverage**, not line or branch coverage. Coverage percentages
may be reported, but they do not gate a release.

| Document | Role |
| --- | --- |
| [Scenario Matrix](../../../test/SCENARIOS.md) | Every required scenario, its layer, gate, and status. |
| [Coverage Registry](../../../test/COVERAGE.md) | Every public API, and the scenarios that cover it. |

## 1. Why This Exists

`master` has 20 test files, and CI runs 10 of them. Its gRPC integration tests call
`GrpcNamingProxy` directly, so they pass while `getAllInstances` on the public client
returns nothing. The rules below exist to prevent that gap.

## 2. Test Layers

| Layer | Needs | Verifies | Required |
| --- | --- | --- | --- |
| Unit | No server. Fake transport and fake clock. | State transitions, error mapping, ordering, cleanup. | Every PR |
| Contract | Fixed vectors. | Wire compatibility with Java: codec and signatures. | Every PR |
| Integration | Real Nacos server. | Public client behavior end to end. | Every PR |
| Package | `npm pack`, then install in a clean project. | Entry points, bridges, and types. | Every PR that touches packaging, and every release |

### 2.1 Unit

- Asynchronous code uses controlled promises and a fake clock. Do not use real sleeps.
- A race is tested in **both completion orders**.
- A test asserts the callback payloads and their order, **and** the final state: source,
  delivery progress, pending work, timers, and errors. Checking one flag is not enough.
- Public behavior is tested through the public client over a fake transport.
  Internal modules may have their own tests in addition.

### 2.2 Contract

Vectors are fixed files in the repository, generated by the reference implementation
and never by the code under test. A test that encodes and decodes with the same code
proves nothing about compatibility. In #157, a fake client that matched the code hid a
Base64 bug that made data unreadable in Java.

### 2.3 Integration

- **Tests use only the public client.** Importing an internal module, such as a proxy or
  `HostReactor`, is not allowed.
- Nacos runs outside the test. Tests read `NACOS_HOST` and `NACOS_PORT`, which default to
  `127.0.0.1` and `8848`.
- Resource names are random. Tests clean up what they create.
- Every client is closed, including when an assertion fails.
- Asynchronous effects use bounded waits with a clear failure message. Fixed sleeps are
  not allowed.
- Functional tests use a non-admin identity with the permissions they need. Admin
  credentials are for fixtures only.
- A test must not create a replacement client to hide a reconnect or token defect.

Assertions check return values, callbacks, and remote side effects. Checking that nothing
threw is not enough.

### 2.4 Package

The test packs the package, installs the tarball into an empty project, and exercises each
entry point. It runs outside the workspace, so that workspace links cannot hide a missing
file or dependency.

## 3. Environments

| Job | Server | Auth | Transport | Purpose |
| --- | --- | --- | --- | --- |
| Unit and contract | None | - | - | Node.js 18, 20, 22, and 24. |
| Integration 3.3.0 | 3.3.0 | On | gRPC | Main functional and auth suite. |
| Integration 3.2.4 | 3.2.4 | Off | gRPC | Previous 3.x line. |
| Integration 2.5.5 | 2.5.5 | Off | gRPC and HTTP | Lowest supported server, and the HTTP regression suite. |
| Reliability | 3.3.0 | On | gRPC | Server restart, short token TTL, and two servers for isolation. |
| Package | None | - | - | Node.js 18 and 24. |

Integration jobs run on Node.js 22. The Reliability job restarts its own server, so that
it cannot disturb other jobs.

The auth suite needs these identities: read-write, read-only, no permission, invalid, and
anonymous.

## 4. Scenario Groups

The first six groups follow
[Required Scenario Groups](https://github.com/alibaba/nacos/blob/3.3.0/specs/en/testing/java-sdk-integration-test-spec.md#3-required-scenario-groups).
The rest are specific to Node.js.

| Group | Prefix | Covers |
| --- | --- | --- |
| Lifecycle | `LC` | Construct, `ready()`, `close()`. |
| Expected capability | `CFG`, `NAM` | Promised remote and local behavior. |
| Boundary and validation | `BND` | Parameters, defaults, idempotent calls. |
| Errors | `ERR` | The error model. |
| Listeners and subscriptions | `CFG`, `NAM` | Delivery, ordering, and cleanup. |
| Authentication | `AUTH` | Identities, tokens, and signatures. |
| Connection | `CON` | Handshake, reconnect, and health. |
| Wire contract | `WIRE` | Compatibility with Java. |
| Encryption plugin | `ENC` | The KMS plugin, tested on its own. |
| Client isolation | `ISO` | Clients must not affect each other. |
| HTTP regression | `HTTP` | The frozen HTTP transport. |
| Migration | `MIG` | Compatibility with released 2.6.x. |
| Packaging | `PKG` | Entry points, bridges, and types. |

## 5. Change Rule

Before changing a public method, option, model, listener behavior, lifecycle behavior, or
error mapping:

1. Find the affected rows in the Scenario Matrix and the Coverage Registry.
2. Add or change scenarios for capability, boundary, listener, and error behavior.
3. Add or change the tests in the same PR, and update the status.

A bug fix adds a scenario that fails before the fix.

If an end-to-end path cannot run in CI, cover validation, boundaries, and controlled
errors, mark the scenario `Documented gap`, and write down why.

## 6. Status

| Status | Meaning |
| --- | --- |
| Covered | A test verifies the scenario at the stated layer, and it runs in CI. |
| Partial | A test verifies part of it, or the test does not go through the 3.x public client. |
| Pending | No test yet. |
| Documented gap | Cannot run in CI. The reason is recorded. |

A test that does not run in CI cannot be `Covered`.

## 7. Release Gates

Each scenario has a **Gate**, the first release that needs it.

| Release | Gate | Must be `Covered` or `Documented gap` |
| --- | --- | --- |
| `3.0.0-beta.1` | `beta` | All `beta` scenarios. |
| `3.0.0-rc.1` | `rc` | All `beta` and `rc` scenarios. |
| `3.0.0` | `ga` | All scenarios except `kms`. |
| KMS release | `kms` | All `kms` scenarios. |

These must also hold for every release:

- All jobs in section 3 pass. A skipped test counts as not run.
- No failing test is retried in CI to make it pass. A flaky test is fixed or removed, and
  its scenario returns to `Pending`.
- `3.0.0` also needs the migration guide and rc verification in a real environment.

A `Documented gap` at a gate needs maintainer agreement in the release PR.

## 8. Existing Tests

The existing tests stay in place until the 3.x layout replaces what they cover. They do
not count as `Covered` unless they meet section 6.

The toolchain migration must either run each existing test file in CI or remove it with a
stated reason. No test file may stay in the repository without running. The
[Coverage Registry](../../../test/COVERAGE.md#existing-test-files) tracks this.

`local_cache.test.ts` from #154 and the #157 regression tests are the base for the
`CFG` scenarios, because they already use controlled ordering.

## 9. Compatibility Baselines

Compatibility tests compare 3.0 with **released 2.6.3**, as listed in
[Released 2.6.x To 3.0](../sdk/sdk-nodejs-impl-spec.md#91-released-26x-to-30). HTTP regression
tests use the same baseline.

`master` is never a baseline. A test that preserves a row of
[Unreleased `master` To 3.0](../sdk/sdk-nodejs-impl-spec.md#92-unreleased-master-to-30) is
wrong, because it treats a defect as a contract. A claim that 3.0 behaves "as in 2.6.x" must
be checked against the `v2.6.3` tag.

## 10. Test Layout

```text
test/
  SCENARIOS.md
  COVERAGE.md
  unit/          Public client over a fake transport, and internal modules
  contract/      Fixed vectors
  integration/   Public client against a real server
  package/       Pack, install, and load
```

Test titles start with the scenario ID, such as `CFG-20: S -> F -> S`, so that the matrix
can be checked against the test files.
